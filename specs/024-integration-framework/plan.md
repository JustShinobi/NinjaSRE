# Plan — 024 Integration Framework

## Summary

Adopt Tracer's integration anatomy and verification framework, extend the base
client for the mandatory credential proxy, add the eleven methodology domain
templates derived from Swapnil's SKILL.md content, and build the scaffold and
catalogue-parameterised contract suite that make Wave 6 finishable.

## Technical context

| Aspect | Choice |
|---|---|
| HTTP | `httpx` async, all traffic through the credential proxy |
| Schemas | Pydantic credential and connection models per integration |
| Discovery | Package walk over `integrations/*`, no central registry |
| Contract suite | `pytest` parameterised over the discovered catalogue |
| Fixtures | Recorded cassettes with secrets scrubbed; live runs on a schedule |
| Scaffold | Template-driven generator producing all seven artefacts |
| Health | Per-integration status recorded and exposed to the console |

## Constitution check

| Article | Satisfaction |
|---|---|
| I | Capabilities return structured evidence with source attribution |
| II | Timeouts, retry ceilings, page-size limits, result caps are named constants |
| III | Every capability declares `side_effect_level`; the scaffold refuses to omit it |
| IV | FR-008, SC-004 — no client can read a credential; enforced by CI |
| V | Runtime-agnostic |
| VI | No provider coupling |
| VII | Integration usage feeds capability effectiveness scoring |
| VIII | `integrations/` tier 2; never imports `capabilities` |
| IX | **Central.** The seven-artefact anatomy is how Article IX scales to 85 vendors |

| XIII | Provenance headers generated by the scaffold |

**Violations:** none.

## The seven artefacts (FR-001)

| # | Artefact | Prevents |
|---|---|---|
| 1 | `schema.py` | Operators guessing what credentials are needed |
| 2 | `verifier.py` | Discovering a wrong token during an incident |
| 3 | `client.py` | Ad-hoc HTTP with inconsistent retry and error handling |
| 4 | `tools/` | Untyped, unplannable, ungoverned capability execution |
| 5 | skill | The agent knowing the API but not the method |
| 6 | `docs.md` | Setup being tribal knowledge |
| 7 | synthetic scenario | The integration silently rotting |

Catalogue validation (FR-002) fails the build on any omission, which is what makes
"full parity" a property rather than an aspiration.

## Domain methodology templates (FR-019, FR-020)

Each encodes the investigative discipline for its class, harvested from Swapnil's
best SKILL.md content:

| Template | Core discipline |
|---|---|
| `logstore` | Statistics before samples: counts, error rate, top patterns, then strategic sampling |
| `metrics` | Establish baseline, find the change point, then correlate — never eyeball a single series |
| `tracing` | Start from an error or slow exemplar, walk the span tree, identify the boundary where latency appears |
| `cloud_control_plane` | Recent changes first, then resource state, then quotas and limits |
| `database` | Active sessions and locks before query plans; replication lag before capacity |
| `vcs` | Deploy timeline first, then the diff in the window, then the specific change |
| `cicd` | Last green build, then the first failure, then the delta between them |
| `ticketing` | Search before create; link rather than duplicate |
| `incident` | Timeline reconstruction; MTTR context; prior similar incidents |
| `communication` | Post structured, link to evidence, never paste raw payloads |
| `data_platform` | Consumer lag and backlog before broker or worker internals |

## Contract suite (FR-013, FR-014)

One suite, parameterised over the discovered catalogue:

```python
@pytest.mark.parametrize("integration", discover_integrations(), ids=lambda i: i.name)
def test_integration_parity(integration): ...
```

Assertions per integration: schema validity, proxy routing, error mapping,
pagination behaviour, capability metadata completeness, skill-to-tool binding,
documentation presence, and at least one synthetic scenario. Adding an integration
adds a parameter, never a file (FR-013).

## Implementation phases

### Phase 1 — Contract suite (test-first)
The parameterised suite with all assertions, plus the catalogue-wide
no-credential-access test. Red against an empty catalogue.

### Phase 2 — Base client
Proxy routing, timeouts, retry, rate limits, three pagination styles, error
taxonomy, regional configuration.

### Phase 3 — Verification framework
Verifier protocol and runner, permission probes, specific failure reporting, the
no-verification-endpoint fallback.

### Phase 4 — Catalogue
Discovery, seven-artefact validation, `CatalogueEntry`, degraded health marking,
exposure to console and docs generation.

### Phase 5 — Domain templates
The eleven methodology templates, each validated to produce a skill passing the
binding check.

### Phase 6 — Scaffold
Generator producing all seven artefacts with provenance headers, taking a domain
to select the template.

### Phase 7 — Proof
Scaffold three real integrations of different shapes and measure the time to a
passing contract suite (SC-001).

## Complexity tracking

| Item | Justification |
|---|---|
| Seven mandatory artefacts | Each maps to a specific historical failure. Making them mandatory at build time is the only mechanism that survives 85 integrations and multiple contributors. |
| A parameterised contract suite rather than per-integration tests | 85 test files would drift; one suite over a discovered catalogue cannot. It also means a framework change is validated against every integration at once. |
| Eleven domain templates | Methodology is the highest-value content in the system and the easiest to get wrong. Templates transfer it rather than hoping each contributor rediscovers it. |
| Degraded marking rather than build failure on live-API breaks | An operator's build should not fail because a vendor shipped a breaking change. Degraded status tells them exactly what is affected. |

## Risks

| Risk | Mitigation |
|---|---|
| The framework is too rigid for an unusual vendor | The base client is composable rather than inheritance-only; an integration may override any layer while keeping proxy routing, which is the one non-negotiable |
| Two hours per integration proves optimistic | SC-001 measures three real integrations of different shapes before Wave 6 commits to the estimate, so the plan adjusts on evidence |
| Domain templates encode wrong methodology | Templates are validated against synthetic scenarios in Wave 7; a template producing worse investigations shows up as a score |
| Recorded fixtures drift from live APIs | Scheduled live runs (FR-015) with degraded marking (FR-016) catch drift within a day |
| Contract suite becomes slow at 85 integrations | Recorded fixtures keep it fast; the live suite runs on a schedule, not on every PR |
