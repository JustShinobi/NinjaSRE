# platform/ — cross-cutting services

**Tier 3.** May import: `config`, `core`. Must never import: `capabilities`, `integrations`, `gateway`, `surfaces`.

Persistence, the credential vault and proxy, the guardrail engine, masking, the
sandbox, memory stores, the knowledge graph, the scheduler, notifications,
identity, reporting delivery, and observability. No investigation logic.

## Conventions

- **This package deliberately shadows the stdlib `platform` module.** It re-exports
  the whole stdlib API so third-party callers are unaffected. Read the footgun in
  the root `AGENTS.md` before touching `__init__.py`.
- No SQL and no Cypher outside `persistence/`. Everything else reaches storage
  through a repository port (Article XI), and `make check-raw-sql` fails the
  build on a query, an `execute` call, or a database driver imported anywhere
  else — including the `importlib` way round it.
- Logging is configured once, in `observability/logging.py`. No other module calls
  `structlog.configure` or `logging.basicConfig`, and a test enforces it.
- This package is the trust boundary. Code here sees credentials; code above it
  never does (Article IV). More precisely: *one module* here sees them —
  `credentials/proxy/resolution.py` — and `make check-credentials` fails the
  build on a `reveal` call anywhere else.

## Storage, in one page

Everything above tier 3 imports from `platform.persistence.ports` and holds a
`PersistenceGateway`. Nothing imports `persistence.postgres` or
`persistence.fakes` — naming a backend is how the second one becomes
unwritable.

```python
async with gateway.begin(scope) as uow:
    await uow.run_traces.record_evidence(evidence)
    await uow.episodes.save(episode)
```

Three things about that snippet are load-bearing.

- **Repositories come from the unit of work.** There is nowhere else to get one,
  so there is no repository outside a transaction. Leaving the block commits;
  raising inside it rolls back, across all twelve.
- **Tenancy comes from the scope, not from arguments.** No port method takes an
  `org_id`, so a cross-tenant read cannot be phrased. The handful of operations
  that genuinely precede tenancy — creating an organisation, resolving a token,
  claiming due jobs, sweeping retention — are `begin_system()`, and that list is
  meant to stay short.
- **The fakes are not test doubles.** `persistence.fakes` passes the same
  contract suite as the Postgres backend and has real transactions. It is what
  lets a feature be built and unit-tested without a database, so a fake that
  drifts is a fiction that feature was written against.

Adding a method to a port means: the protocol, the fake, the Postgres
repository, a case in the port's contract suite, and — if it is tenant-scoped —
a case in `tests/contract/persistence/test_tenant_isolation.py`, which fails if
you forget.

## The PostgreSQL backend

`make verify` runs the contract suite against the fakes. **`make test-postgres`
runs the same suite against a real PostgreSQL**, and SC-005 is not satisfied
until it has — it is a CI job of its own because it builds an image and creates
a database per test. Run it before changing anything under `persistence/`.

Four things about that backend are load-bearing and non-obvious:

- **Tenancy is in the primary key**, not in a `WHERE` clause. Every tenant-scoped
  table is keyed `(org_id, …)` and every foreign key is composite, so a child row
  *cannot* reference a parent in another organisation. Losing a filter is a bug;
  it is not a data leak.
- **Vectors live one table per generation.** pgvector fixes a column's width at
  creation, and a re-embed may change it (FR-014), so `begin_generation` creates
  a table, `activate_generation` moves one integer, and `drop_generation` is a
  `DROP TABLE`. Those tables are data, not schema — `env.py` keeps them out of
  autogenerated migrations.
- **Cypher runs on the driver connection, not through `text()`.** Cypher's label
  syntax is `(n:Node)` and SQLAlchemy reads `:Node` as a bind parameter. It is
  the same connection and transaction, so a graph write still commits with
  everything beside it.
- **AGE will not parameterise a traversal depth.** `graph/queries.py` renders one
  statement per legal depth at import, and a validated integer selects one. No
  caller text ever reaches a query.

Migrations are autogenerated (`alembic -c platform/persistence/migrations/alembic.ini
revision --autogenerate`) and every one carries a `downgrade` that is tested.

## Credentials, in one page

The vault and the proxy are two halves of Article IV, split along the line that
makes the claim checkable.

**`credentials/vault.py` cannot read a credential.** There is no `reveal` on
`Vault` and there never will be — FR-003 says a value must not be returned to
any caller outside the proxy, and the way to make that true is the absence of a
method rather than a check that could be removed. Everything an operator, a
console, or a health check does goes through here and works on
`CredentialVersion`, which has no field that could hold a value.

**`credentials/proxy/` is the only thing that can.** Read `proxy/engine.py`
first: it is the sequence, and the order is the design. The allow-list runs
*before* the vault, so a request that acquired a hostile URL — the realistic
route being a prompt-injected log line — cannot make the proxy decrypt anything.

Four things about it are load-bearing and non-obvious:

- **Rotation writes a version; it does not overwrite.** Each version is its own
  row and a pointer row's *metadata labels* name the live one. So rolling back is
  a label move rather than a restore from somebody's password manager, and
  reading which version is live never touches a value.
- **Nothing is cached.** One vault read per proxied request, which is what makes
  rotation take effect immediately — the alternative is a rotated credential
  that keeps working for fifteen minutes nobody budgeted for.
- **There is no bypass, under any configuration.** No flag, no environment
  variable, no degraded mode. A deployment without a working proxy is one where
  authenticated calls fail loudly, because a fallback is the switch that gets
  flipped during an outage and never flipped back.
- **The `dev` mount and the `standard` service are one object.** `ProxyApp` is a
  plain ASGI callable; the dev profile drives it in-process and the standard
  profile serves it over a socket. A test stands up a real socket and asserts
  both produce the same vendor request and the same classified refusal.

Adding a vendor means a package under `integrations/`, not a change here. A
signing scheme is the exception: signing needs the key, so it is a
`RequestSigner` in `proxy/signing/`.

## Where things go

- A repository port and its Postgres implementation → `persistence/`.
- A new graph traversal → `persistence/ports/topology_graph.py`, as a named,
  bounded method. The catalogue is closed on purpose: no port here accepts a
  query string, which is what stops an LLM-generated one ever being executed.
- Anything that touches a secret → `credentials/`, behind the proxy. Only
  `CredentialStore.reveal` returns secret material, and only the proxy calls it.
- A service the agent uses but does not reason about → its own subpackage here,
  not into `core/`.
