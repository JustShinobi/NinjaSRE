# Briefing 070 — confianca-de-certificado

**Essência**: um Proxmox comum — certificado self-signed, o default de
instalação — conecta; e ou o deployment confia no certificado que o operador
declarou, ou recusa **nomeando o certificado**, nunca "no node answered".
Mudança de fronteira de segurança, desenhada como tal (backlog "A vendor with
a self-signed certificate cannot be connected"). Backend
(`platform/credentials/proxy` + `integrations/proxmox`); par do slot S3 com a
030 — não toca single-write (a mensagem de painel que precisar de i18n é
declarada no relatório).

## O que a spec precisa cobrir

1. **O mecanismo existente vira caminho.** `integrations/proxmox/certificates.py`
   já tem `CertificateTrust` com as três formas — fingerprint pinado, PEM
   fornecido, `unverified(reason=…, accepted_by=…)` — e
   `integrations/proxmox/docs.md` documenta as três. Nada as carrega:
   nenhum campo de schema, nenhum caminho de configuração, `ProxmoxClient`
   recebe `DEFAULT_TRUST`. A spec liga: schema → armazenamento → **egress do
   proxy**, porque o handshake TLS acontece lá (uma decisão expressa no
   client não alcança nada — o fato central do backlog).
2. **Desenho de fronteira, explícito no spec**: quem pode aceitar um
   certificado não verificado (permissão dedicada?); a aceitação é por
   vendor ou por endereço (recomendação do plan com rationale); o que a
   auditoria grava (quem, quando, fingerprint aceito, razão); o que acontece
   quando o certificado do vendor muda (pin quebrado ⇒ recusa nomeando o
   novo fingerprint, nunca fallback silencioso).
3. **`unverified` é decisão registrada, não flag**: a forma da API interna já
   força `reason` e `accepted_by` — o caminho de configuração preserva isso
   (nada de checkbox "skip TLS verify" solto).
4. **Generalização honesta**: o mecanismo nasce no Proxmox mas a fronteira é
   do proxy — o plan decide se o carrier é genérico (qualquer vendor
   self-hosted com endereço) já nesta feature ou Proxmox-first com o shape
   genérico preparado. Não sobre-entregar: o DoD é o Proxmox real conectando.
5. **A mensagem certa em cada falha**: certificado não confiado ⇒ frase
   nomeando o certificado (fingerprint) e o caminho para confiar; rede de
   fato fora ⇒ a mensagem de hoje. As duas nunca se confundem.
6. **Console mínimo**: o campo/fluxo para colar fingerprint/PEM ou registrar
   aceitação na tela da integração — reusar o padrão de campos declarados
   (`credential_fields`/schema) para não inventar UI nova; textos i18n via
   relatório (030 é a dona no slot).

## Riscos

- É **a** mudança sensível da onda: o único lugar onde verificação TLS pode
  ser enfraquecida é o proxy, e a spec trata qualquer vazamento disso para
  outro componente como violação (Artigo IV na prática).
- Sandboxes nunca falam com o proxy — nada muda nisso.
- Teste real: staging tem o Proxmox de verdade (pve02) com self-signed — o
  acceptance de staging é conectar e ver o estate começar a povoar
  (read-only; a descoberta é leitura).
- Segredo nenhum em log/audit — fingerprint não é segredo; a chave privada e
  o token são.

## DoD

Proxmox do homelab Verified no staging com trust declarado (fingerprint ou
PEM); auditoria mostrando a aceitação; pin errado recusado com o fingerprint
na mensagem; estate com recursos do Proxmox (`/resources` deixa de estar
vazio); testes de contrato do proxy para os três modos; `make verify` verde.
