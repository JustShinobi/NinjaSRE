Check what came up, and what did not:

  kubectl -n {{ .Release.Namespace }} get pods -l app.kubernetes.io/instance={{ .Release.Name }}
  kubectl -n {{ .Release.Namespace }} port-forward svc/{{ include "ninjasre.fullname" . }}-app {{ .Values.app.port }}
  curl localhost:{{ .Values.app.port }}/health/ready

Readiness names the dependency that is not ready rather than answering yes or
no, so a pod that will not become ready has already told you why.

{{- if not .Values.encryptionKey.secret.name }}

WARNING: no encryption-key secret is configured. NinjaSRE will not generate one
— a key it generated would live in this release's stored values and be
discovered missing during a restore, on somebody else's watch. Create it before
configuring an integration:

  openssl rand -base64 32 | kubectl -n {{ .Release.Namespace }} create secret generic ninjasre-encryption-key --from-file=key=/dev/stdin
{{- end }}

Back up before every upgrade. The whole deployment is one PostgreSQL instance,
so `sh deploy/ops/backup.sh` is the whole procedure and its manifest is what
makes restoring into a different release a decision rather than a gamble.
