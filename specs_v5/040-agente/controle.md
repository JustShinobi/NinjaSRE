## Lista de paridade (insumo para a 070)

Grupos de schema que estas três páginas agora cobrem, campo a campo:

- **`models.*`** — completo. 8 papéis × `{provider, model}` = 16 campos, todos editáveis, com herança.
- **`surfaces.notification_policy.*`** — completo. 6/6 campos (`quiet_hours_enabled`, `quiet_hours_start`, `quiet_hours_end`, `timezone`, `cooldown_seconds`, `notifications_per_hour`).
- **`policies.autonomy.*`** — parcial. Cobertos: `rules` (criação com escopo + nível), `freezes` (criação), `budgets` (criação), `overrides` (grant/revoke, pré-existente), `dry_run`. **Não cobertos**: `allow_unverifiable_actions`, `recurrence_threshold`, `recurrence_window_seconds` — três campos escalares do mesmo grupo, sem controle nesta página (nem tinham antes). Editar um rule/freeze/budget/override *existente* granularmente (além do nível de uma rule) também não foi construído — só criação.
- **`policies.masking.*`** — quase completo via `ConfigEditor`: `enabled`, `level`, `custom_patterns` (lista de objetos, `ConfigEditor` já sabe editar isso). 3/3 campos.
- **`policies.guardrails.*`** — parcial via `ConfigEditor`: `mode`, `ruleset` editáveis; `disabled_rules` (lista de strings simples) **não** é editável pelo `ConfigEditor` reaproveitado — é uma limitação preexistente do componente (`console/src/surfaces/preview.tsx`, `isObjectList`/`EDITABLE_TYPES` não cobrem array-de-string), não introduzida por mim, mas herdada.
- **`policies.approvals.*`** — parcial pelo mesmo motivo: `threshold`, `expiry_hours` editáveis; `autonomous_capabilities` (lista de strings) não.

**Para a 070**: os campos de lista-de-string (`policies.guardrails.disabled_rules`, `policies.approvals.autonomous_capabilities`, e potencialmente outros no restante do schema) precisam de uma extensão do `ConfigEditor` compartilhado — ou de um controle dedicado — antes que a paridade seja 100% nesses dois grupos. Nomeado aqui para não virar uma "lista cheia e errada".

## Descobertas que mudam como alguém deve rodar os gates ou ler o código a partir de agora

1. **`console/src/surfaces/settings/resolution-preview.tsx` é `'use client'`; funções puras que um componente servidor precisa chamar (não só renderizar) não podem morar lá.** `tests/unit/shell/rsc-boundary.test.ts` pegou isso quando `models.tsx`/`notifications.tsx` chamavam `valueAt()` de lá. Corrigido extraindo para `console/src/surfaces/settings/values.ts` (sem diretiva). Um re-export do módulo cliente **não** resolve — o próprio comentário do teste diz isso, e eu tropecei nisso antes de ler com atenção.
2. **Uma função como prop de servidor para cliente só quebra em build real.** `models.tsx` passava `integrationsHref` (uma função) para `<ModelsEditor>`. Todos os 2091 testes vitest passavam; o `tsc`/`eslint` não acusavam nada. Só apareceu ao rodar `python -m tools.console_e2e run` contra o **build de produção real** (`.next/standalone`), com o erro literal do Next: "Functions cannot be passed directly to Client Components...". Corrigido movendo a função para dentro do próprio módulo cliente. **Isto é exatamente a classe de defeito que `tests/unit/shell/rsc-boundary.test.ts` descreve em seu próprio docstring como já tendo acontecido três vezes** — esta é a quarta, e só o e2e real (não o gate de vitest/tsc/eslint) a pegou. Quem construir a próxima página deste grupo deveria rodar o e2e pelo menos uma vez antes de declarar pronto, não só os gates de unidade.
3. **`Promise.all` sobre N leituras paralelas dentro de um único painel é frágil: um provider falhando derruba a página inteira.** `models.tsx` fazia `Promise.all` sobre as 9 leituras de `/v1/providers/{id}`; corrigido para `Promise.allSettled`, descartando as que falharem em vez de derrubar o painel inteiro. Achado via o mesmo e2e real — via curl direto contra o mock, todas as 9 respondem 200 isoladamente, mas alguma combinação sob carga do Next real falhava sem eu conseguir isolar exatamente qual nem por quê a tempo; a resiliência estrutural (`allSettled`) é a correção correta de qualquer forma.
4. **`console/src/app/api/config/route.ts` e `.../preview/route.ts` descartavam `remove` do corpo, enviando só `patch`.** Achado ao construir "devolver à herança" para Models (que depende de `remove` chegar ao gateway).
