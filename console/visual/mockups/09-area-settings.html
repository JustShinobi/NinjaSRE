Rework da área de Settings

Diagnóstico das seis telas de configuração percorridas de ponta a ponta em Full HD, e a proposta de reorganização — navegação, catálogo de integrações, onboarding e o destino do editor de configuração cru.

Este documento é a referência visual da área Settings. Ele registra duas decisões: navegação híbrida — Integrations permanece entrada própria na barra lateral e o restante vira uma entrada Settings com navegação secundária — e a substituição integral do editor de configuração cru por telas humanas. Âncoras #mockup-1 a #mockup-4 nomeiam cada tela; as telas que os implementam citam este arquivo no registro visual.

Parte 1

Diagnóstico, tela por tela

O padrão que se repete: cada tela mistura três coisas — o formulário que muda o sistema, a documentação que explica o conceito, e o estado atual — num único fluxo vertical sem hierarquia. E quando uma tela precisa apontar para outra, ela aponta para /configuration, que é um editor de schema, não uma tela de produto.

TelaGravidadeProblemas observados
/integrations Crítica
  • 84 cards em lista plana alfabética; 11.730px de altura (13 telas). Os 2 configurados somem no meio de 82 vazios.
  • Sem busca, sem categorias, sem logos. Único filtro ("Connection: Any / Not connected / Unchecked / Verified") não cobre a pergunta principal — "o que eu uso?".
  • Nomes crus (azure_monitor, better_stack) e duas linhas redundantes de estado por card ("No credential is stored…" + "no credential is stored for this node").
  • A API já devolve category, summary, capabilities e suggested — a UI ignora tudo isso.
  • Formulário de credencial inline com labels cruas ("token", "project"), sem link de onde obter a credencial.
  • No rodapé, "Not covered, and why": nove parágrafos densos de documentação dentro da tela de configuração.
/configuration Crítica
  • É um editor de schema: tabela "Effective configuration" com JSON bruto e 38 acordeões nomeados por chave pontilhada em monospace (policies.observation.bridge.metrics).
  • É também o destino dos CTAs das outras telas — o caminho "feliz" do produto termina num despejo de schema.
  • Autonomy, integrações e notificações são editáveis aqui e nas telas próprias: dois lugares para a mesma verdade.
/first-run (Setup) Média
  • Conceito bom (checklist com "You are here"), mas três painéis mostram o mesmo estado com vocabulários diferentes: "2 of 7 steps left", "stored, unchecked", "it answered", "Nobody has checked this one".
  • Ids crus (google_gemini) ao lado de nomes próprios ("Google Gemini").
  • O check funciona e o diagnóstico é excelente ("o modelo respondeu sem chamar a ferramenta — escolha um modelo com tool calling"), mas vem como parágrafo denso sem ação clicável.
/signals Média
  • Aba Intake mistura documentação de webhook (payload, headers, assinatura) com ferramenta de teste — texto técnico denso por receptor.
  • Aba Destinations: o texto manda conectar integração "in the catalogue", mas o botão diz "Open configuration" e joga no editor de schema.
  • Contagem divergente: Setup diz "2 of 7 steps left"; a aba Continuous observation diz "3 step(s) are outstanding".
/autonomy Média
  • Empty state "No policy recorded" aponta "Look at the configuration" — loop entre as duas telas que editam a mesma coisa.
  • Painel "Save this posture" com label crua (deployment · —) e três botões sem hierarquia ("Explain one action", "Simulate everything", "What would this decide differently?").
  • Três parágrafos conceituais (rule / bound / override) antes de qualquer controle.
/administration Média
  • Machine tokens: ~15 linhas idênticas "bootstrap — investigation.read, token.manage — HEALTHY" sem agrupamento nem explicação do acúmulo.
  • Formulário de SSO (8 campos OIDC) enterrado no fim da aba People.
  • Aba Audit contradiz a si mesma: o link diz "default — 200 events", o painel diz "Nothing has been recorded".
  • Botão "Widen the period" não faz nada (opção quebrada confirmada).
Parte 2

A causa raiz é a arquitetura de informação

Os seis itens do grupo "Settings" estão organizados pela arquitetura interna do software (catálogo, pipeline, política, schema, identidade), não pelas perguntas de quem configura. A proposta: uma única entrada Settings com navegação secundária própria — o padrão de Linear, Vercel e Stripe — organizada por intenção, onde cada página é a dona do seu domínio e o editor cru vira uma saída de emergência em "Advanced".

Parte 3

Regras transversais para a spec

Um domínio, uma donaCada domínio tem exatamente uma tela que o edita. O editor cru é substituído por completo: um mapa de paridade grupo-do-schema → tela dona, verificado automaticamente, garante que nenhum campo fica órfão (spec 070).
Vocabulário único de estadoQuatro palavras para credenciais em todo o produto: Não conectada · Armazenada · Verificada · Falhando. Fim de "it answered", "HEALTHY", "stored, unchecked" convivendo.
Nome de exibição obrigatórioTodo id de catálogo tem display name e categoria visíveis; o id cru (google_gemini) aparece só em contexto técnico (API, audit).
CTA aterrissa no alvoTodo empty state aponta para a tela + âncora que resolve, com o verbo certo ("Conectar uma integração de chat"), e nunca para o editor cru.
Documentação recolhidaReferência (payloads de webhook, "not covered") vive em painéis recolhíveis ou páginas de referência — nunca no fluxo entre o operador e o formulário.
Ajuda mora no campoNada de subtítulo de prosa sob o título da página (subtítulo de dado — contagens, "Passo N de 7" — pode). A frase de ajuda aparece sob o controle que ela explica, vinda do field_help/section_help que o schema já declara. Tooltip nunca carrega informação essencial.
Rolagem é bugNenhuma tela de configuração passa de ~2 viewports em 1080p. Listas longas ganham busca, filtro e paginação por construção.

Correções pontuais que a spec deve absorver: consertar "Widen the period" (hoje é no-op), reconciliar "200 events" × "Nothing recorded" no Audit, unificar a contagem de passos do Setup, e agrupar os machine tokens repetidos do bootstrap com expurgo em massa.

Análise feita em 14 ago 2026 sobre o front local (preview 3101) em 1920×1080, com o backend do repositório. HTML estático, sem interação: layout, hierarquia, agrupamento e vocabulário são normativos; pixels exatos não.
